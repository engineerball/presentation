Release บ่อยแค่ไหน? — นั่นแหละจุดอ่อน

เดือนละครั้ง

Code ก้อนใหญ่ 10x → Root Cause หายาก → War Room

อาทิตย์ละครั้ง

Build Time นานขึ้น → Cost พุ่ง → ต้อง Optimize Pipeline

หลายครั้ง/สัปดาห์

Focus ย้าย → Output → Outcome (Business Impact)

4 คำที่ต้องแยก: Deploy ≠ Release ≠ Output ≠ Outcome

Deploy = ขึ้น server · Release = เปิดให้ user · Output = ทำเสร็จ · Outcome = สร้าง impact

3 Approaches

OpenAI · Anthropic · Stripe

OpenAI — Environment-First Harness

จากแอป Sora Android — โค้ด 1 ล้านบรรทัด คนไม่เขียนเอง

Distributed Context

AGENT.md / SKILL.md กระจายในทุก Module → AI ต้องอ่านก่อนเขียน

Strict Dependencies

Types → Config → Repo → Service → Runtime → UI (บังคับลำดับ)

CI/CD Feedback

Test ผ่านไหม? ไม่ผ่าน → โยน Error กลับให้ AI แก้เองวนจนผ่าน

ผลลัพธ์: 1,500 PRs · 3→7 engineers · ~3.5 PRs/engineer/day

Anthropic — Multi-Agent Decoupling

ปัญหา: AI ตรวจโค้ดตัวเอง → เข้าข้างตัวเองเสมอ → รายงานว่า "สมบูรณ์แบบ" แม้โค้ดพัง

Stripe — One-Shot Minions

Production-scale ใน monorepo ใหญ่ — ส่ง task 1 อย่าง รับ PR 1 อย่าง

Blueprints

Feedforward guides ระดับ service ที่ encode architectural rules — เหมือน AGENT.md แต่เจาะลึกแต่ละ service

Pre-push Hooks

Lint + Type Check + Test รันก่อน push → Agent self-correct ถ้า fail → คนไม่ต้องเข้ามาเกี่ยว

Key insight: ไม่ใช้ multi-agent วน loop แต่ใช้ Feedforward (Blueprints) + Feedback (Hooks) ที่ lightweight กว่า

Trade-off #1: แพงเกิน

$9

Single agent — งานเดียว

$200

Multi-agent (Anthropic)

Agent ตีกันเอง: Planner สั่ง → Generator เขียนผิด → Evaluator ตำหนิ → Generator แก้ไข → Evaluator ตำหนิอีก → วน loop เผา Token ไปเป็นร้อยดอลลาร์

ท้ายสุด Dev ก็ต้องเหนื่อยมาเขียน Code ทำ Orchestration คิวงานให้อยู่ดี

Trade-off #2: Test ผ่าน ≠ โค้ดดี

CI/CD บอก

✓ Test ผ่านทุกอัน

Code ไม่พัง syntax ถูก type ผ่าน

ความจริง

✗ Architecture พัง

Maintain ต่อไม่ได้ · Rule ทับซ้อน · เพิ่ม Debt แทนที่จะลด

ตลกเรียกว่า "Test-Passing Illusion" — โค้ดผ่านฉลุย แต่เปิดดูแล้วน้ำตาไหล

พิเศษ: Greenfield Project ที่ยังไม่มี Architecture ตั้ง Rule ก็เท่ากับนั่งเทียนเขียน

Enterprise

  • Architecture Fitness Tests
  • E2E Validation (Playwright)
  • Cost Monitoring per task

Regulated

Financial / Healthcare

  • Audit Trail (append-only log)
  • Security Gates
  • Evaluation Loop (Agent review Agent)

Skills ที่ควรมีใน Harness

ควรมี

Onboarding — สรุป arch + conventions ให้ AI รู้ว่าอยู่ตรงไหน

PR Review — Lint + Type-check + Convention violations อัตโนมัติ

E2E Validation — รันผ่าน Browser/API จริง (Playwright)

Cost Monitor — ตาม token usage, idle loop detection

ไม่ควรมี (เกินไป)

Over-detailed code generation rules (AI เขียนดีกว่ากฎแล้ว)

Unnecessary intermediate steps (AI มองรวมได้ดีขึ้น)

Redundant validation layers (เช็คซ้ำซ้อน เปลือง cost)

Vercel lesson: ลบ 80% → แม่นขึ้น
