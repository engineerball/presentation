Section 1

Quick Recap

Cloud in 5 Minutes

 Why Cloud?

  • Scale on demand — no more capacity planning guesswork
  • Global infrastructure — deploy close to users in minutes
  • Pay for what you use — shift from owning hardware to consuming services
  • Innovation velocity — 200+ products, new features weekly
  • Managed services — reduce operational burden (patching, scaling, DR)

 Key insight: Cloud isn't "putting your servers somewhere else" — it's consuming capabilities as APIs that you used to build and maintain yourself.

 Pricing Basics

Model Discount Best For Commitment
On-Demand — Dev/test, spiky workloads None
SUDs (Auto) Up to 30% Any sustained usage Automatic
CUDs Up to 57% Steady baseline workloads 1-3 year
Preemptible/Spot Up to 91% Batch, fault-tolerant jobs None (can reclaim)

 SUDs are automatic — no action needed. Run a VM for >25% of the month, discount kicks in. CUDs for stable baseline. Don't commit to CUDs for unstable workloads.

Section 4

Data Engineering

Big Data Platform on GCP

 Modern Data Platform — Big Picture

SOURCES

Apps, DBs, APIs, IoT

INGEST

Pub/Sub, Dataflow, Fusion

STORE

GCS (Lake), BigQuery (WH)

PROCESS

Dataflow, Dataproc, BQ

SERVE

Looker, Vertex AI, APIs

 GCP advantage: Decoupled storage and compute. Store data in GCS (cheap), process with BigQuery/Dataflow (fast). Pay for what you scan, not for idle clusters.

 BigLake — One engine queries both warehouse (BigQuery native) and lake (GCS: Parquet, ORC, Iceberg, Delta Lake) data in place.

 Data Ingestion

Service Type Best For
Pub/Sub Real-time Event streaming, real-time pipelines
Dataflow Batch + Streaming ETL/ELT, complex transformations
Cloud Data Fusion Visual No-code/low-code data pipelines
Datastream CDC Replicating database changes in real-time

 Real-time vs Batch: Real-time when you need data within seconds (fraud detection, live dashboards). Batch when you can wait (daily reports, warehousing). Use Lambda architecture — real-time for immediate insights, batch for corrections.

 Data Lake & Warehouse

 GCS — Data Lake

Store raw data in open formats (Parquet, Avro, ORC)

  • Auto lifecycle policies: Standard → Nearline → Coldline → Archive
  • Bucket-level IAM, Object-level ACLs

 BigQuery — Data Warehouse

Serverless, columnar, petabyte-scale

  • Pay per data processed, not per cluster
  • BigLake: query GCS data in place
  • BI Engine: in-memory caching

 BigQuery cost tip:

Billing is per data scanned. Always partition and cluster tables. Never SELECT * on large tables.

BigQuery ML (BQML)

Train ML models with SQL — no data export needed. Great for starting out before graduating to Vertex AI.

 Orchestration & Analytics

Cloud Composer Managed Airflow

DAGs define task dependencies, schedule + retry built-in

Best for: complex ETL with many dependencies

Workflows Serverless

YAML step definitions, no infra to manage

Best for: API orchestration, conditional logic

Looker BI

Semantic layer, embedded analytics, data apps

Vertex AI ML Platform

AutoML, custom training, model deployment, feature store

 Rule: Complex pipelines → Composer. Simple orchestration → Workflows. Don't over-engineer.

Section 5

Networking & Security

What Most People Miss

 VPC Design Best Practices

Private-first approach

No public IPs on workloads when possible

Shared VPC

Central networking team manages VPC, projects attach to it

VPC Service Controls

Security perimeters around GCP APIs (BigQuery, GCS)

Private Service Connect

Access Google APIs via private endpoints

 Common mistake: Using default VPC for production — no segmentation, no isolation, hard to add later.

 VPC Service Controls create a perimeter around API data. Even if credentials are compromised, data cannot be exfiltrated. Many orgs skip this layer.

 IAM Best Practices

Principle of Least Privilege

Grant minimum permissions needed — no more

One Service Account per Workload

Don't share — enables audit and rotation

Workload Identity Key!

GKE pods auth as GCP service accounts — no key files!

Custom Roles

Fine-grained permissions when predefined roles don't fit

 Common mistakes:

  • Using roles/owner or roles/editor for everything
  • Storing service account keys in code / containers
  • One service account for all workloads
  • Never rotating credentials

 Prefer predefined roles:

roles/storage.objectViewer instead of roles/editor

 Cloud Armor & BeyondCorp

Cloud Armor

  • DDoS protection + WAF
  • Preconfigured rules: SQLi, XSS, LFI, RFI
  • Rate limiting, geo-blocking
  • Adaptive Protection (ML-based)

Attached to External HTTP(S) Load Balancer

BeyondCorp Enterprise

  • Zero-trust access — no VPN needed
  • Context-aware: identity + device + location
  • IAP: Protect internal apps
  • Access Context Manager

Replace VPN with identity-based access

 Free WAF rules are available — no reason not to enable them. Use IAP instead of VPN for internal app access whenever possible.

Section 6

Well-Architected

Production Readiness Checklist

 GCP Well-Architected Framework

 Reliability

Can it recover from failures? Automated backups? Failover?

 Security

Encrypted? Least-privilege IAM? Incident response plan?

 Cost Optimization

Right pricing model? Idle resources? Budget alerts?

 Operational Excellence

Monitoring? Alerting? CI/CD? Incident management?

 Production Checklist

  • IAM: No owner/editor on service accounts, Workload Identity
  • Networking: Private IPs only, Cloud NAT, Cloud Armor
  • Monitoring: SLO alerts, uptime checks enabled
  • Logging: Cloud Audit Logs at org level
  • Cost: Budget alerts set, no unused resources
  • Data: Encrypted at rest + in transit, backup configured
  • CI/CD: All infra changes through code review
  • DR: Documented failover plan, tested at least once

 Ship this checklist with every project. It takes 5 minutes to verify. It takes hours to recover from things you forgot.

ETL Pipeline with Dataflow + BigQuery

 Workshop Overview

What we'll build:

↓

Tools

Learning Outcomes

  • Understand ETL pipeline on GCP
  • Write & run Apache Beam pipelines
  • Use BigQuery for transformation
  • Monitor Dataflow jobs

Based on GSP290 — Google Cloud Skills

 Pre-Lab Setup

Enable APIs:

# Enable required APIs gcloud services enable dataflow.googleapis.com \ compute.googleapis.com storage.googleapis.com \ bigquery.googleapis.com cloudaicompanion.googleapis.com

Download starter code:

gcloud storage cp -r \ gs://spls/gsp290/dataflow-python-examples .

Create resources:

# Create GCS bucket gcloud storage buckets create \ gs://$PROJECT_ID/ --location=$REGION # Copy data files gcloud storage cp gs://spls/gsp290/data_files/*.csv \ gs://$PROJECT_ID/data_files/ # Create BigQuery dataset bq mk lake

Note: If using Google Skills lab, project is pre-configured. APIs may just need a restart.

 Step 1: Data Ingestion Pipeline

Pipeline logic (data_ingestion.py):

# Pipeline steps: # 1. Read CSV from GCS (TextIO) # 2. Filter out header row # 3. Parse lines → dictionaries # 4. Write to BigQuery (BigQueryIO) with beam.Pipeline() as p: (p | 'Read' >> beam.io.ReadFromText(input) | 'Filter' >> beam.Filter( lambda line: 'name,state' not in line) | 'Parse' >> beam.Map(parse_line) | 'Write' >> beam.io.WriteToBigQuery( table, schema=schema))

Setup Docker:

docker run -it \ -e PROJECT=$PROJECT_ID \ -v $(pwd)/dataflow-python-examples:/dataflow \ python:3.8 /bin/bash pip install apache-beam[gcp]==2.59.0 cd /dataflow

 Runner modes:

DirectRunner = local testing
DataflowRunner = distributed on GCP

 Step 1: Run Ingestion Pipeline

Run the pipeline:

python dataflow_python_examples/data_ingestion.py \ --project=$PROJECT_ID \ --region=$REGION \ --runner=DataflowRunner \ --machine_type=e2-standard-2 \ --staging_location=gs://$PROJECT_ID/test \ --temp_location=gs://$PROJECT_ID/test \ --input=gs://$PROJECT_ID/data_files/head_usa_names.csv \ --save_main_session

 Monitor: Navigate to Dataflow in Console. Watch job status. Wait for "Succeeded" (~5 min).

Verify in BigQuery:

SELECT * FROM lake.usa_names LIMIT 10;

 Step 2: Data Transformation Pipeline

What's different?

Same ingestion + adds data transformation

  • Ingest CSV from GCS
  • Parse lines → dictionaries
  • Transform year format → BigQuery DATE
  • Write to BigQuery

This is the "T" in ETL — the most important step in production pipelines.

Run:

python dataflow_python_examples/\ data_transformation.py \ --project=$PROJECT_ID \ --region=$REGION \ --runner=DataflowRunner \ --machine_type=e2-standard-2 \ --staging_location=gs://$PROJECT_ID/test\ --temp_location=gs://$PROJECT_ID/test \ --input=gs://$PROJECT_ID/data_files/\ head_usa_names.csv \ --save_main_session

 Step 3: Enrich with BigQuery SQL

Query and analyze:

-- Join and enrich data SELECT state, gender, COUNT(*) as name_count, AVG(year) as avg_year FROM lake.usa_names WHERE year > 2000 GROUP BY state, gender ORDER BY name_count DESC LIMIT 20;

 BigQuery power:

  • Serverless — no cluster management
  • Processes TBs in seconds
  • Optimizes query execution automatically
  • Pay per data scanned

Try your own queries! Change the WHERE clause, add different GROUP BY, JOIN with other tables.

Section 8

Lessons Learned

War Stories from the Trenches

 Things We Learned the Hard Way

🔥 Over-provisioning

16 vCPU for an app using 2 → $3,000/month wasted

→ Fix: Cloud Monitoring → rightsized to e2-standard-2

🔥 BigQuery Cost Surprise

SELECT * on 5TB unpartitioned table → $25 in one query

→ Fix: Always partition + cluster, SELECT specific columns

🔥 Open Firewall "Temporarily"

0.0.0.0/0 on port 22 "for debugging" → forgot to close → crypto miner

→ Fix: Use IAP for SSH, never expose SSH

🔥 Silent Pipeline Failure

Dataflow failed silently for 3 days → stale reports

→ Fix: Alerting on failures + data freshness checks

 Tips & Tricks

1. Always set budget alerts — first thing after project creation

2. Use labels consistently — enable billing breakdown by team/project

3. Enable all audit logs at org level — you'll need them

4. Use Terraform for everything — click-ops will bite you

5. Test in a separate project — never experiment in production

6. Read the Recommender — Active Assist finds idle resources, security issues, optimization opportunities

7. Start simple, iterate — Cloud Run before GKE, MIG before custom autoscaling
